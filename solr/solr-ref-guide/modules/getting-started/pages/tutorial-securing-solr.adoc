This tutorial introduces authentication and authorization using a two-node SolrCloud example.
You will configure HTTPS and ZooKeeper access control, verify the certificate with curl, create users with Basic Authentication and Rule-Based Authorization, and try requests with different permissions.
The example loads the same techproducts data used in xref:tutorial-techproducts.adoc[].

Authentication identifies the user making a request.
Authorization determines what that user may do.
A correct password does not grant access to every API: the user's roles must also allow the requested operation.

== Before You Begin

Run the commands from your Solr installation directory.
This tutorial assumes you are familiar with the basics in xref:solr-tutorial.adoc[].
The `secure-setup` example requires Unix or macOS, with `curl` and OpenSSL available on your path.
Windows is not supported; the example exits before creating files or starting nodes.
To configure security manually on Windows, see xref:deployment-guide:enabling-ssl.adoc[], xref:deployment-guide:basic-authentication-plugin.adoc[], and xref:deployment-guide:zookeeper-access-control.adoc[].
The default ports `8983`, `8984`, and `9983` must be available.

[WARNING]
====
This is a local learning environment with demonstration passwords.
The wizard generates HTTPS files before configuring the demonstration accounts.
Basic Authentication does not encrypt credentials; this example uses HTTPS to protect HTTP connections.
A production deployment also needs network restrictions and a secured ZooKeeper ensemble.
See xref:deployment-guide:securing-solr.adoc[] for deployment guidance.
====

== Secure SolrCloud Example

=== Interactive Startup

The `bin/solr` script walks you through setting up HTTPS, choosing account passwords, and starting a secured SolrCloud cluster on your workstation.
To get started, run:

[source,bash]
----
bin/solr start -e secure-setup
----

This starts an interactive session with a greeting like this:

[source,text]
----
Welcome to the secure SolrCloud example!
This example uses demonstration credentials. Change them before using it outside your local environment.
----

We'll use the default passwords throughout this exercise.
The script starts two Solr nodes on the same machine, using different ports to represent separate servers.
The first node also runs embedded ZooKeeper.

=== Choose a Keystore Password

First, the script asks for a password to protect the HTTPS keystore:

[source,text]
----
Generating sample PEM certificate and key files. OpenSSL must be available on PATH.
The generated self-signed certificate is valid for 30 days and is for local use.
----

You'll see this prompt:

[source,text]
----
Keystore password [SolrRocks]:
----

Press Enter to accept `SolrRocks` for this exercise.
You can choose a different password of at least six characters if you prefer.
This password protects the TLS keystore; you'll choose the account passwords next.

The script uses OpenSSL to generate a self-signed certificate and private key covering `localhost` and `127.0.0.1`, then creates the Java keystore and truststore.
The wizard prints the paths to the generated certificate, private key, keystore, truststore, keystore-password file, and example-specific include file under `example/secure-setup/tls`.
It does not edit the installation-wide `solr.in.sh`.

=== Choose Account Passwords

Next, the script asks whether you want to change the demonstration account passwords:

[source,text]
----
The solr, index, search, zk-admin, and zk-readonly accounts use SolrRocks by default.
----

At the following prompt, press Enter to keep the defaults:

[source,text]
----
Change account passwords? [y/N]:
----

If you choose `y`, the script asks for a password for each account; passwords typed at an interactive terminal are hidden.
A password equal to its username is rejected by default, and the wizard asks for another password.
If you customize passwords, substitute them in the commands below.
The HTTP accounts become active after you verify HTTPS in the next step.

The wizard prints the paths where credentials are saved, with owner-only permissions on POSIX filesystems:

* `example/secure-setup/http-credentials.properties`: HTTP account passwords.
* `example/secure-setup/zk-credentials.properties`: ZooKeeper digest account passwords.

`zk-admin` has full access to the example's ZooKeeper data.
`zk-readonly` can read ordinary metadata but cannot modify it or read `/security.json` and `/security/*`.
These accounts are independent of the HTTP users.
The example-specific include file configures digest authentication and ACLs for Solr and CLI commands, using the `/solr` ZooKeeper chroot.
The example does not enable TLS for ZooKeeper connections.

=== Verify HTTPS

The script now starts the first node with HTTPS enabled.
Before it enables HTTP authentication, it asks you to check the connection from another terminal:

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem \
  'https://localhost:8983/api/node/system'
----

Run the command in another terminal.
You should receive system information without a certificate error.
Return to the wizard at this prompt:

[source,text]
----
Press Enter after curl verifies HTTPS to continue:
----

Press Enter.
The script enables HTTP authentication, starts the second node, creates the `techproducts` collection, and loads 31 sample documents using the `index` account.
The wizard does not run curl itself.
If you are restarting an example with authentication enabled, an HTTP 401 response also confirms that HTTPS is working; the saved credentials are reused when restarting the example.

=== Check Your Cluster

When startup finishes, you should see messages like these:

[source,text]
----
Secure Solr example running at https://localhost:8983/solr/. Sign in as solr. You will need to accept the self-signed certificate in the browser.
Second node running at https://localhost:8984/solr/. Sign in as solr.
----

You now have the following local cluster:

[%autowidth,options="header"]
|===
|Process |Port |Solr home
|First Solr node |`8983` |`example/secure-setup`
|Second Solr node |`8984` |`example/secure-setup-node2`
|Embedded ZooKeeper |`9983` |Hosted by the first node
|===

The `techproducts` collection has two shards, with one replica per shard and one shard on each node.
It uses `sample_techproducts_configs`, just like the techproducts example.
Both nodes share the first home's TLS files and use the same HTTP and ZooKeeper accounts.
The script prints the paths to `http-credentials.properties` and `zk-credentials.properties` when it finishes.
A private copy of the ZooKeeper credentials is also saved in the second node's home.

If startup fails, check `example/secure-setup/logs/solr.log` and `example/secure-setup-node2/logs/solr.log`.

=== HTTP Account Permissions

[%autowidth,options="header"]
|===
|Username |Default password |Access
|`solr` |`SolrRocks` |Security, collection, and configuration administration; no document indexing or searching
|`index` |`SolrRocks` |Indexing and searching
|`search` |`SolrRocks` |Searching
|===

=== Starting with --no-prompt

You can also start a fresh example with all the defaults instead of answering the interactive prompts:

[source,bash]
----
bin/solr start -e secure-setup --no-prompt
----

All account passwords and the keystore password default to `SolrRocks`.
`--no-prompt` prints the curl verification command but does not pause for you to run it.
When restarting an existing example, it reuses saved passwords and configuration rather than resetting them to the defaults.

Saved ZooKeeper credentials are reused on subsequent starts.
An existing example with unsecured ZooKeeper data requires a fresh Solr home or an offline ACL migration; the wizard does not rewrite existing ACLs while Solr is running.
See xref:deployment-guide:zookeeper-access-control.adoc[] for migration instructions and production considerations, including ZooKeeper transport security.

== Sign In to the Admin UI

Open https://localhost:8983/solr/[the first node's Solr Admin UI] or https://localhost:8984/solr/[the second node's Admin UI] in your browser.
Accept the browser warning for the self-signed certificate generated for this local example.
Sign in with username `solr` and password `SolrRocks`, unless you chose different administrator credentials.

The startup command labels the Admin UI "Secure Solr Setup" using `-Dsolr.environment=prod,label=Secure+Solr+Setup`.
Open https://localhost:8983/solr/#/~cloud[Cloud → Graph] to see how the two shards are distributed across the nodes.

The Security screen lets the administrator inspect and manage users, roles, and permissions.
To query documents in the Admin UI, sign in as `search` or `index`, select the `techproducts` collection, and open its Query screen.
Run the default `\*:*` query to see the sample documents.
An administrator query or document update receives HTTP 403 because those data-access roles are not assigned to the administrator.

== Try Authentication and Authorization

=== Check Health and Metrics Without Credentials

Run these commands without `--user`:

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem 'https://localhost:8983/api/node/health'
curl --cacert example/secure-setup/tls/cert.pem -H 'Accept:' 'https://localhost:8983/api/metrics'
----

Both requests succeed without authentication; HTTPS still protects the connection.
The metrics command suppresses curl's default `Accept: */*` header so the endpoint uses its default Prometheus output format.
The same checks work on the second node at port `8984`.
An existing example retains its stored security configuration on restart.
Use a fresh Solr home to generate this configuration if your example was created with different settings.

=== Query Without Credentials

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem -i 'https://localhost:8983/solr/techproducts/select?q=*:*&rows=0'
----

The request returns HTTP `401 Unauthorized` because it has no credentials.
The `read` permission requires the `search` role, so authorization challenges anonymous document queries even though `blockUnknown` is `false`.
An incorrect password also produces a 401 response.

=== Query as the Search User

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem --user search:SolrRocks 'https://localhost:8983/solr/techproducts/select?q=*:*&rows=0'
----

This request succeeds.
The response's `numFound` value is `31` on a fresh example.
The search user's role grants the `read` permission.

=== Verify Communication Between Nodes

The wizard posts all sample documents through the first node.
Because the two shards are placed on different nodes, some updates must be forwarded to the second node over HTTPS.
A distributed query through either node should return all 31 documents on a fresh example:

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem --user search:SolrRocks \
  'https://localhost:8984/solr/techproducts/select?q=*:*&rows=0'
----

Compare that with a query restricted to the shard local to each node:

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem --user search:SolrRocks \
  'https://localhost:8983/solr/techproducts/select?q=*:*&rows=0&distrib=false'
curl --cacert example/secure-setup/tls/cert.pem --user search:SolrRocks \
  'https://localhost:8984/solr/techproducts/select?q=*:*&rows=0&distrib=false'
----

Each local result contains only part of the data; the two counts add up to 31.
The full query therefore verifies authenticated communication between the two nodes.
The layout has no redundant replicas: both nodes must be running to query all shards, and stopping the first node also stops ZooKeeper.

=== Try an Update as the Search User

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem -i --user search:SolrRocks \
  -H 'Content-Type: application/json' \
  --data-binary '[{"id":"secure-example-product","name":"Secure example product"}]' \
  'https://localhost:8983/solr/techproducts/update?commit=true'
----

This request returns HTTP `403 Forbidden`.
The password is valid, but the user's roles do not grant the `update` permission.
The document is not added.

=== Index as the Indexing User

Send the same update through the second node using the indexing account:

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem --user index:SolrRocks \
  -H 'Content-Type: application/json' \
  --data-binary '[{"id":"secure-example-product","name":"Secure example product"}]' \
  'https://localhost:8984/solr/techproducts/update?commit=true'
----

This request succeeds because the indexing user's `index` role grants `update`.
Query the new document with the search account:

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem --user search:SolrRocks \
  'https://localhost:8983/solr/techproducts/select?q=id:secure-example-product'
----

== Create Another Search User

Creating an account and assigning its permissions are separate steps.
As the administrator, create a user named `reader`:

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem --user solr:SolrRocks \
  -H 'Content-Type: application/json' \
  --data-binary '{"set-user":{"reader":"ReaderRocks"}}' \
  'https://localhost:8983/api/cluster/security/authentication'
----

Assign the existing `search` role to that user:

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem --user solr:SolrRocks \
  -H 'Content-Type: application/json' \
  --data-binary '{"set-user-role":{"reader":["search"]}}' \
  'https://localhost:8983/api/cluster/security/authorization'
----

The node reloads security changes asynchronously.
Once the new configuration has loaded, query with the new credentials:

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem --user reader:ReaderRocks 'https://localhost:8983/solr/techproducts/select?q=*:*&rows=0'
----

For details on changing passwords and permission rules, see xref:deployment-guide:basic-authentication-plugin.adoc[] and xref:deployment-guide:rule-based-authorization-plugin.adoc[].

== Stop and Restart

[source,bash]
----
bin/solr stop -p 8984
bin/solr stop -p 8983
----

Stop the second node before the first, because the first hosts ZooKeeper.
Run `bin/solr start -e secure-setup` again to restart both nodes.
Existing security settings are preserved, and an existing collection is not reindexed or resharded.
For an older one-shard example, use a fresh, existing `--solr-home` directory to create the two-shard layout used in this tutorial.
Saved HTTP and ZooKeeper passwords are reused without prompting.
If you changed the administrator password through an API, supply the new credentials when restarting:

[source,bash]
----
bin/solr start -e secure-setup --credentials solr:NewPassword
----

After the supplied credentials successfully authenticate, the example saves them for subsequent starts.
Changing a password in the saved HTTP credentials file updates what the wizard uses; it does not change the server's password.

== Use the CLI with the Secured Example

=== Reuse the Example Settings

Subsequent runs reuse the certificate and HTTPS settings under `example/secure-setup/tls`.
The generated self-signed certificate is intended only for this local exercise.
Your browser will warn about it; a certificate from a publicly trusted CA avoids that warning.

Other `bin/solr` commands can use the example's HTTPS and ZooKeeper credentials by selecting its include file.
For example, check the node's status with the HTTP administrator credentials:

[source,bash]
----
SOLR_INCLUDE=example/secure-setup/tls/solr.in.sh bin/solr status --credentials solr:SolrRocks
----

The wizard ends by printing a ZooKeeper listing command. With the default credentials, run:

[source,bash]
----
bin/solr zk ls / --zk-host localhost:9983/solr --zk-credentials zk-admin:SolrRocks
----

This authenticates directly to ZooKeeper without the example's include file or HTTPS settings.
The output lists the example's znodes, including `collections`, `configs`, and `security.json`.
The HTTP `--credentials` option authenticates Solr discovery requests; `--zk-credentials` supplies ZooKeeper digest credentials.
For a customized ZooKeeper password, replace `SolrRocks` with the value saved in `zk-credentials.properties`.
The HTTP and ZooKeeper properties files contain passwords in plain text; their owner-only file permissions protect them locally.
HTTP passwords stored in ZooKeeper's `security.json` are salted hashes instead.

The read-only account can list collection metadata:

[source,bash]
----
bin/solr zk ls /collections --zk-host localhost:9983/solr --zk-credentials zk-readonly:SolrRocks
----

It cannot read the security configuration:

[source,bash]
----
bin/solr zk ls /security.json --zk-host localhost:9983/solr --zk-credentials zk-readonly:SolrRocks
----

The second command fails with `NoAuth`.

Compare this with a request that does not load the example's credentials:

[source,bash]
----
SOLR_INCLUDE=/dev/null SOLR_ZK_CREDS_AND_ACLS='' bin/solr zk ls / --zk-host localhost:9983/solr
----

This command fails with `NoAuth`, demonstrating that the ACLs require authentication for access to the example's data.

=== Replace or Renew the Certificate

The wizard reuses its TLS files on restart; it does not automatically renew the 30-day certificate.
Obtain a replacement certificate and private key covering `localhost` and `127.0.0.1`, then stop both nodes as shown above.
Use `bin/solr ssl` with the replacement PEM files, `--solr-include-file example/secure-setup/tls/solr.in.sh`, and `--keystore example/secure-setup/tls/solr-ssl.keystore.jks`.
Keep the default `JKS` store type: the wizard uses it when loading the truststore on restart.
Also update `example/secure-setup/tls/cert.pem`, `key.pem`, and `keystore-password.txt` to match the replacement certificate, key, and keystore password.
Restart with `bin/solr start -e secure-setup`; both nodes share the updated TLS files.
See xref:deployment-guide:enabling-ssl.adoc#install-an-existing-pem-certificate[Install an Existing PEM Certificate] for details.

== Understand the Security Configuration

The first node uses `example/secure-setup` as its Solr home.
The wizard starts that node, writes the security configuration to `/security.json` within the ZooKeeper `/solr` chroot, and waits for authentication to become active before starting the second node, creating the collection, or indexing data.

=== The Generated security.json

For the default accounts, the wizard creates the following configuration.
Password hashes are replaced with placeholders here; the stored values contain a salted hash and salt, not the passwords themselves.

[source,json]
----
{
  "authentication": {
    "class": "solr.BasicAuthPlugin",
    "blockUnknown": false,
    "credentials": {
      "solr": "<salted password hash>",
      "index": "<salted password hash>",
      "search": "<salted password hash>"
    }
  },
  "authorization": {
    "class": "solr.RuleBasedAuthorizationPlugin",
    "permissions": [
      {"name": "security-edit", "role": "superadmin"},
      {"name": "security-read", "role": "admin"},
      {"name": "config-edit", "role": "admin"},
      {"name": "config-read", "role": "admin"},
      {"name": "collection-admin-edit", "role": "admin"},
      {"name": "core-admin-edit", "role": "admin"},
      {"name": "core-admin-read", "role": "admin"},
      {"name": "read", "role": "search"},
      {"name": "collection-admin-read", "role": ["admin", "search"]},
      {"name": "update", "role": "index"},
      {"name": "health", "role": null},
      {"name": "metrics-read", "role": null},
      {
        "name": "public-monitoring",
        "collection": null,
        "path": ["/____v2/node/health", "/____v2/metrics"],
        "method": "GET",
        "role": null
      },
      {"name": "all", "role": "admin"}
    ],
    "user-role": {
      "solr": ["superadmin", "admin"],
      "index": ["index", "search"],
      "search": ["search"]
    }
  }
}
----

`authentication` verifies supplied Basic Authentication credentials.
`blockUnknown: false` lets requests without credentials reach authorization, where the permission rules decide whether they are allowed.
Invalid credentials are still rejected.

`authorization` maps users to roles and checks permission rules in order.
The `health` and `metrics-read` rules have `role: null`, allowing these endpoints without credentials.
The `public-monitoring` rule also permits anonymous GET requests to the two v2 monitoring paths during the initial routing authorization check.
Solr internally routes `/api` requests through `/solr/____v2`, so the permission paths use the internal `/____v2` prefix.
`collection: null` limits this rule to node-level requests.
These rules precede the final `all` rule, which requires the `admin` role for otherwise unmatched requests.
Document reads require `search`, and updates require `index`, even for the administrator.
The administrator has only `superadmin` and `admin`; `superadmin` grants security configuration changes.
The indexing user has `index` and `search`; the search-only user has `search`.
The wizard loads the sample documents over HTTPS using the `index` account.

In SolrCloud, security settings are shared through ZooKeeper.
Editing a local `security.json` file in the Solr home does not change the cluster configuration.

== Choose Different Ports or Directories

To use another Solr home, create an empty directory and pass it with `--solr-home`.
Use `-p` to select the first node's port:

[source,bash]
----
mkdir -p example/my-secure-setup
bin/solr start -e secure-setup --solr-home example/my-secure-setup -p 9000
----

This starts Solr on ports `9000` and `9001`, with embedded ZooKeeper on `10000`.
The second node uses the sibling home `example/my-secure-setup-node2`.
Choose a first-node port at or below `64535`, and make sure all three ports are available.
Substitute your paths and ports in the commands in this exercise.
See xref:deployment-guide:solr-control-script-reference.adoc#start-and-restart[Start and Restart] for other startup options.
