This exercise starts a two node Solr cluster, enables HTTPS, assigns separate administration, indexing, and search accounts, and protects ZooKeeper data with access control lists (ACLs).
You will verify HTTPS for both client requests and requests between Solr nodes.
Each step uses the tools included in the Solr distribution, JDK `keytool`, OpenSSL, and `curl`.

Use a fresh full Solr installation on Unix or macOS, with ports 8983, 8984, and 9983 available.
Run the commands in the same Bash-compatible shell, from the installation directory, using an installation path without spaces.
Do not run these commands against an existing cluster.

IMPORTANT: This exact setup is not ready or appropriate for production use.
It is a local learning exercise with demonstration passwords and a shared self-signed certificate.
Keep the cluster on loopback.
ZooKeeper authentication and ACLs do not encrypt its connection; this exercise leaves ZooKeeper transport on loopback without TLS.
For deployment guidance, see xref:deployment-guide:securing-solr.adoc[], xref:deployment-guide:enabling-ssl.adoc[], and xref:deployment-guide:zookeeper-access-control.adoc[].

== Start Two Nodes

Prepare two isolated Solr homes by copying the distribution's configuration files.
Then start the first node with the ordinary `bin/solr start` command:

[source,bash]
----
umask 077  # Makes new files and directories accessible only to your user
export TUTORIAL_HOME="$PWD/tutorial/secure"
mkdir -p "$TUTORIAL_HOME/node1/solr" "$TUTORIAL_HOME/node2/solr" "$TUTORIAL_HOME/tls"
for node in node1 node2; do
  cp server/solr/solr.xml "$TUTORIAL_HOME/$node/solr/"
  cp server/solr/zoo.cfg "$TUTORIAL_HOME/$node/solr/"
done
cat > "$TUTORIAL_HOME/tls/solr.in.sh" <<EOF
SOLR_ULIMIT_CHECKS=false
SOLR_HOST_BIND=127.0.0.1
SOLR_HOST_ADVERTISE=127.0.0.1
SOLR_PID_DIR="$TUTORIAL_HOME"
SOLR_OPTS="-Dsolr.security.allow.paths=$TUTORIAL_HOME"
EOF
export SOLR_INCLUDE="$TUTORIAL_HOME/tls/solr.in.sh"
SOLR_LOGS_DIR="$TUTORIAL_HOME/node1/logs" \
  bin/solr start --solr-home "$TUTORIAL_HOME/node1/solr"
----

`SOLR_ULIMIT_CHECKS=false` suppresses resource-limit warnings for this local exercise.

`SOLR_LOGS_DIR` gives each node its own log directory.

The first SolrCloud node listens on `localhost:8983` and starts embedded ZooKeeper on `localhost:9983`.
The embedded ZooKeeper is suitable for this exercise; production clusters should use an external ensemble.

Check that it responds over HTTP, then start the second node:

[source,bash]
----
curl --fail 'http://localhost:8983/api/node/health'
SOLR_LOGS_DIR="$TUTORIAL_HOME/node2/logs" \
  bin/solr start -p 8984 --solr-home "$TUTORIAL_HOME/node2/solr" -z localhost:9983
curl --fail 'http://localhost:8984/api/node/health'
curl --fail --silent --show-error \
  'http://localhost:8983/api/cluster/nodes'
----

Wait for each health request to succeed before proceeding; repeat the corresponding `curl` command if the node is still initializing.
A listening TCP port alone does not mean Solr has finished starting.

Both nodes use ZooKeeper's root namespace.
The first node runs embedded ZooKeeper; the second joins it with `-z localhost:9983`.
Each home starts with only configuration files and stores its own data.

The response's `nodes` array must contain two nodes, with ports 8983 and 8984.
If only one node appears, repeat the `curl` command after the second node finishes initializing; continue when both are present.
Both nodes share the first node's ZooKeeper, rather than forming separate clusters.
The working directory holds both nodes' data, certificates, and a private configuration file.
Node logs are under `tutorial/secure/node1/logs` and `tutorial/secure/node2/logs`.

== Create a Certificate and PKCS12 Stores

Generate a private key and self-signed certificate directly in a PKCS12 keystore.
The `-ext 'SAN=...'` option below sets the certificate's subject alternative names, so the certificate is considered valid for both `localhost` and `127.0.0.1`, the two names used in this exercise:

[source,bash]
----
keytool -genkeypair -alias solr-ssl -keyalg RSA -keysize 2048 \
  -validity 365 -dname 'CN=localhost' \
  -ext 'SAN=DNS:localhost,IP:127.0.0.1' \
  -storetype PKCS12 -keystore "$TUTORIAL_HOME/tls/solr-ssl.keystore.p12" \
  -storepass SolrRocks -keypass SolrRocks
keytool -exportcert -alias solr-ssl -rfc \
  -keystore "$TUTORIAL_HOME/tls/solr-ssl.keystore.p12" -storetype PKCS12 \
  -storepass SolrRocks -file "$TUTORIAL_HOME/tls/cert.pem"
keytool -importcert -noprompt -alias solr-ssl \
  -file "$TUTORIAL_HOME/tls/cert.pem" \
  -keystore "$TUTORIAL_HOME/tls/solr-ssl.truststore.p12" -storetype PKCS12 \
  -storepass SolrRocks
openssl x509 -in "$TUTORIAL_HOME/tls/cert.pem" -noout -subject -dates -text
----

The keystore contains the private key and certificate presented by each server.
The truststore contains the certificate trusted by Solr's outbound HTTPS clients.
The PEM certificate lets `curl` verify the server without disabling certificate checks.
Using the same keystore on both nodes simplifies the exercise; real deployments should manage certificates and private keys separately for each node.

== Enable HTTPS on Both Nodes

Solr only applies include-file changes when a node starts, so this section rewrites the include file and then stops and restarts both nodes to pick up HTTPS.

Write an include file used only for this exercise.
The unquoted heredoc expands the absolute working-directory path now; escaped dollar signs preserve variables for later launches:

[source,bash]
----
cat > "$TUTORIAL_HOME/tls/solr.in.sh" <<EOF
SOLR_ULIMIT_CHECKS=false
SOLR_HOST_BIND=127.0.0.1
SOLR_HOST_ADVERTISE=127.0.0.1
SOLR_PID_DIR="$TUTORIAL_HOME"
SOLR_OPTS="-Dsolr.security.allow.paths=$TUTORIAL_HOME"
SOLR_SSL_ENABLED=true
SOLR_SSL_KEY_STORE="$TUTORIAL_HOME/tls/solr-ssl.keystore.p12"
SOLR_SSL_KEY_STORE_PASSWORD=SolrRocks
SOLR_SSL_KEY_STORE_TYPE=PKCS12
SOLR_SSL_TRUST_STORE="$TUTORIAL_HOME/tls/solr-ssl.truststore.p12"
SOLR_SSL_TRUST_STORE_PASSWORD=SolrRocks
SOLR_SSL_TRUST_STORE_TYPE=PKCS12
SOLR_SSL_CLIENT_TRUST_STORE="\${SOLR_SSL_CLIENT_TRUST_STORE:-$TUTORIAL_HOME/tls/solr-ssl.truststore.p12}"
SOLR_SSL_CLIENT_TRUST_STORE_PASSWORD=SolrRocks
SOLR_SSL_CLIENT_TRUST_STORE_TYPE=PKCS12
SOLR_SSL_NEED_CLIENT_AUTH=false
SOLR_SSL_WANT_CLIENT_AUTH=false
SOLR_SSL_CHECK_PEER_NAME=true
EOF
chmod 600 "$TUTORIAL_HOME/tls/solr.in.sh"
----

The server's truststore and the outbound client's truststore are explicit.
Nodes advertise the IPv4 loopback address `127.0.0.1`; client URLs can also use `localhost`, because the certificate covers both.
Hostname verification remains enabled.
Client certificates are not required; later steps authenticate users with Basic Authentication over HTTPS.

Stop the second node before stopping the first node and its embedded ZooKeeper, then restart both with the updated include file:

[source,bash]
----
bin/solr stop -p 8984
bin/solr stop -p 8983
export SOLR_INCLUDE="$TUTORIAL_HOME/tls/solr.in.sh"
SOLR_LOGS_DIR="$TUTORIAL_HOME/node1/logs" \
  bin/solr start -p 8983 --solr-home "$TUTORIAL_HOME/node1/solr"
SOLR_LOGS_DIR="$TUTORIAL_HOME/node2/logs" \
  bin/solr start -p 8984 --solr-home "$TUTORIAL_HOME/node2/solr" -z localhost:9983
----

Verify each node with the trusted PEM certificate:

[source,bash]
----
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" \
  'https://localhost:8983/api/node/health'
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" \
  'https://127.0.0.1:8984/api/node/health'
----

Both requests should succeed.
A request without the certificate should fail certificate verification, because your operating system does not trust this self-signed certificate.
Plaintext HTTP requests to either port should fail:

[source,bash]
----
curl --fail 'https://localhost:8983/api/node/health'
curl --fail 'http://localhost:8983/api/node/health'
curl --fail 'http://localhost:8984/api/node/health'
----

Do not use `curl -k` to bypass verification.

== Authenticate Users and Assign Roles

Enable Basic Authentication with the existing control-script command.
It writes authentication settings into the private include file and creates `basicAuth.conf` beside it:

[source,bash]
----
SOLR_HOME="$TUTORIAL_HOME/tls" bin/solr auth enable --type basicAuth \
  --credentials admin:SolrRocks --block-unknown true -z localhost:9983
chmod 600 "$TUTORIAL_HOME/tls/basicAuth.conf" "$SOLR_INCLUDE"
----

The security configuration is shared through ZooKeeper, so both nodes enforce it.
The command's `SOLR_HOME` override selects the directory for `basicAuth.conf`; it does not change either running node's home.
The bootstrap account initially has all template roles.
Use the authentication API to set passwords for the indexing and search accounts:

[source,bash]
----
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" -u admin:SolrRocks \
  -H 'Content-Type: application/json' \
  --data '{"set-user":{"index":"SolrRocks","search":"SolrRocks"}}' \
  https://localhost:8983/api/cluster/security/authentication
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" -u admin:SolrRocks \
  -H 'Content-Type: application/json' \
  --data '{"set-user-role":{"admin":["superadmin","admin"],"index":["index","search"],"search":["search"]}}' \
  https://localhost:8983/api/cluster/security/authorization
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" -u admin:SolrRocks \
  https://localhost:8983/api/cluster/security/authorization
----

Inspect the permission list in the last response.
In the built-in template, `collection-admin-read` is permission index 9 and grants only the `search` role.
Allow both `admin` and `search` to inspect collection state:

[source,bash]
----
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" -u admin:SolrRocks \
  -H 'Content-Type: application/json' \
  --data '{"update-permission":{"index":9,"role":["admin","search"]}}' \
  https://localhost:8983/api/cluster/security/authorization
----

The accounts now have these responsibilities:

[cols="1,2",options="header"]
|===
|Account |Permissions
|`admin` |Manage security, configuration, and collections; cannot index or search.
|`index` |Index documents and search.
|`search` |Search; cannot index documents.
|===

The predefined `read` and `update` permissions take precedence over the template's final `all` permission.
Removing `index` and `search` roles from `admin` therefore separates administration from document access.
For permission details, see xref:deployment-guide:rule-based-authorization-plugin.adoc[].

== Protect ZooKeeper Data

Solr user accounts do not protect direct ZooKeeper access.
Create separate digest credentials for ZooKeeper administration and read-only inspection:

[source,bash]
----
cat > "$TUTORIAL_HOME/tls/zk-credentials.properties" <<'EOF'
zkDigestUsername=zk-admin
zkDigestPassword=SolrRocks
zkDigestReadonlyUsername=zk-readonly
zkDigestReadonlyPassword=SolrRocks
EOF
chmod 600 "$TUTORIAL_HOME/tls/zk-credentials.properties"
printf '\n' >> "$SOLR_INCLUDE"
cat >> "$SOLR_INCLUDE" <<EOF
SOLR_ZK_CREDS_AND_ACLS="-DzkCredentialsInjector=org.apache.solr.common.cloud.VMParamsZkCredentialsInjector -DzkCredentialsProvider=org.apache.solr.common.cloud.DigestZkCredentialsProvider -DzkACLProvider=org.apache.solr.common.cloud.DigestZkACLProvider -DzkDigestCredentialsFile=$TUTORIAL_HOME/tls/zk-credentials.properties"
SOLR_OPTS="\$SOLR_OPTS \$SOLR_ZK_CREDS_AND_ACLS"
EOF
tail -n 2 "$SOLR_INCLUDE"
bin/solr stop -p 8984
bin/solr stop -p 8983
SOLR_LOGS_DIR="$TUTORIAL_HOME/node1/logs" \
  bin/solr start -p 8983 --solr-home "$TUTORIAL_HOME/node1/solr"
SOLR_LOGS_DIR="$TUTORIAL_HOME/node2/logs" \
  bin/solr start -p 8984 --solr-home "$TUTORIAL_HOME/node2/solr" -z localhost:9983
bin/solr zk updateacls / -z localhost:9983
ADMIN_ZK_OPTS='-DzkCredentialsInjector=org.apache.solr.common.cloud.VMParamsZkCredentialsInjector -DzkCredentialsProvider=org.apache.solr.common.cloud.DigestZkCredentialsProvider -DzkACLProvider=org.apache.solr.common.cloud.DigestZkACLProvider -DzkDigestUsername=zk-admin -DzkDigestPassword=SolrRocks'
SOLR_INCLUDE=/dev/null SOLR_ZK_CREDS_AND_ACLS="$ADMIN_ZK_OPTS" \
  bin/solr zk updateacls /security.json -z localhost:9983
----

The `tail` command displays the two settings just appended to the include file.
`SOLR_ZK_CREDS_AND_ACLS` configures command-line ZooKeeper clients; adding the same settings to `SOLR_OPTS` also configures each server.
The servers authenticate as `zk-admin` and create znodes with administrator access plus read-only access for `zk-readonly`.
The `zk-readonly` account is for direct inspection of ordinary cluster metadata; Solr nodes do not use it.
The first `updateacls` command migrates existing znodes: changing the provider alone would leave their previous ACLs in place.
When using ZooKeeper's root namespace, explicitly restrict `/security.json` to the administrator with the second command, which omits the read-only credentials.
This protects the Solr passwords stored there.
Repeat that command after any future ACL migration of the entire tree.

Check administrator access:

[source,bash]
----
bin/solr zk ls / -z localhost:9983
----

For a read-only CLI session, pass only the read-only user's credentials, using the injector's primary username/password fields.
This authenticates the client as that user without supplying the administrator secret:

[source,bash]
----
READONLY_ZK_OPTS='-DzkCredentialsInjector=org.apache.solr.common.cloud.VMParamsZkCredentialsInjector -DzkCredentialsProvider=org.apache.solr.common.cloud.DigestZkCredentialsProvider -DzkDigestUsername=zk-readonly -DzkDigestPassword=SolrRocks'
SOLR_INCLUDE=/dev/null SOLR_ZK_CREDS_AND_ACLS="$READONLY_ZK_OPTS" \
  bin/solr zk ls /collections -z localhost:9983
printf 'read-only probe\n' > "$TUTORIAL_HOME/readonly-probe.txt"
SOLR_INCLUDE=/dev/null SOLR_ZK_CREDS_AND_ACLS="$READONLY_ZK_OPTS" \
  bin/solr zk cp "$TUTORIAL_HOME/readonly-probe.txt" zk:/readonly-probe -z localhost:9983
SOLR_INCLUDE=/dev/null SOLR_ZK_CREDS_AND_ACLS="$READONLY_ZK_OPTS" \
  bin/solr zk cp zk:/security.json "$TUTORIAL_HOME/forbidden-security.json" -z localhost:9983
SOLR_INCLUDE=/dev/null SOLR_ZK_CREDS_AND_ACLS= \
  bin/solr zk ls / -z localhost:9983
----

The directory listing as `zk-readonly` succeeds.
The attempted write, the read of `security.json`, and the anonymous listing must fail with authorization errors.
These ACLs control access but do not provide transport encryption.

== Index and Verify Distributed HTTPS Queries

Create a collection with two shards and one replica per shard, using the techproducts configuration, then index the sample XML documents as `index`:

[source,bash]
----
bin/solr create -c techproducts --shards 2 --replication-factor 1 \
  -d sample_techproducts_configs --credentials admin:SolrRocks \
  -s https://localhost:8983
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" -u admin:SolrRocks \
  'https://localhost:8983/api/collections?detailed=true&collection=techproducts'
bin/solr post -c techproducts --credentials index:SolrRocks \
  -s https://localhost:8983 example/exampledocs/*.xml
----

Check that `collectionsDetail.techproducts.shards` reports one shard replica on port 8983 and the other on port 8984, both `active`, with `https://` base URLs.
Each node should hold only part of the collection.

Query through both nodes as `search`, asking Solr to include shard details:

[source,bash]
----
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" -u search:SolrRocks \
  'https://localhost:8983/api/collections/techproducts/select?q=*:*&rows=0&shards.info=true'
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" -u search:SolrRocks \
  'https://localhost:8984/api/collections/techproducts/select?q=*:*&rows=0&shards.info=true'
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" -u search:SolrRocks \
  'https://localhost:8983/api/collections/techproducts/select?q=*:*&rows=0&distrib=false'
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" -u search:SolrRocks \
  'https://localhost:8984/api/collections/techproducts/select?q=*:*&rows=0&distrib=false'
----

The distributed requests return the same total `numFound` and show two responding shard addresses under `shards.info`.
The bundled XML examples produce 31 documents.
Every address must start with `https://`, including the remote node.
With `distrib=false`, each node returns its local shard's count; the two local counts add up to the distributed total.
This confirms that a full query requires communication between the nodes.

Verify the role boundaries and anonymous access.
The first three requests should return HTTP 403; the last two should return HTTP 401:

[source,bash]
----
curl --cacert "$TUTORIAL_HOME/tls/cert.pem" -u search:SolrRocks \
  -H 'Content-Type: application/json' --data '[{"id":"forbidden"}]' \
  -w '\nHTTP %{http_code}\n' https://localhost:8983/api/collections/techproducts/update
curl --cacert "$TUTORIAL_HOME/tls/cert.pem" -u admin:SolrRocks \
  -w '\nHTTP %{http_code}\n' 'https://localhost:8983/api/collections/techproducts/select?q=*:*'
curl --cacert "$TUTORIAL_HOME/tls/cert.pem" -u admin:SolrRocks \
  -H 'Content-Type: application/json' --data '[{"id":"forbidden-admin"}]' \
  -w '\nHTTP %{http_code}\n' https://localhost:8983/api/collections/techproducts/update
curl --cacert "$TUTORIAL_HOME/tls/cert.pem" -w '\nHTTP %{http_code}\n' \
  'https://localhost:8983/api/collections/techproducts/select?q=*:*'
curl --cacert "$TUTORIAL_HOME/tls/cert.pem" -w '\nHTTP %{http_code}\n' \
  'https://localhost:8984/api/collections/techproducts/select?q=*:*'
----

== Test Trust Between the Nodes

A successful `curl` request verifies curl's trust in the server.
To also test the outbound trust used by Solr, temporarily give node 2 a truststore containing an unrelated certificate.
Keep the normal server keystore and truststore unchanged:

[source,bash]
----
keytool -genkeypair -alias unrelated -keyalg RSA -keysize 2048 \
  -validity 1 -dname 'CN=unrelated' -storetype PKCS12 \
  -keystore "$TUTORIAL_HOME/tls/unrelated-keystore.p12" \
  -storepass SolrRocks -keypass SolrRocks
keytool -exportcert -alias unrelated -rfc -storetype PKCS12 \
  -keystore "$TUTORIAL_HOME/tls/unrelated-keystore.p12" -storepass SolrRocks \
  -file "$TUTORIAL_HOME/tls/unrelated-cert.pem"
keytool -importcert -noprompt -alias unrelated -storetype PKCS12 \
  -file "$TUTORIAL_HOME/tls/unrelated-cert.pem" \
  -keystore "$TUTORIAL_HOME/tls/untrusted-truststore.p12" -storepass SolrRocks
bin/solr stop -p 8984
SOLR_SSL_CLIENT_TRUST_STORE="$TUTORIAL_HOME/tls/untrusted-truststore.p12" \
SOLR_LOGS_DIR="$TUTORIAL_HOME/node2/logs" \
  bin/solr start -p 8984 --solr-home "$TUTORIAL_HOME/node2/solr" -z localhost:9983
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" -u admin:SolrRocks \
  'https://localhost:8983/api/node/health'
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" -u admin:SolrRocks \
  'https://localhost:8984/api/node/health'
----

Wait for node 2's replica to finish loading before testing the distributed query.
Inspect collection state and confirm a local query succeeds:

[source,bash]
----
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" -u admin:SolrRocks \
  'https://localhost:8983/api/collections?detailed=true&collection=techproducts'
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" -u search:SolrRocks \
  'https://localhost:8984/api/collections/techproducts/select?q=*:*&rows=0&distrib=false'
----

Repeat these checks until both replicas are `active` and the local query returns node 2's document count.
Then issue the distributed query:

[source,bash]
----
curl --cacert "$TUTORIAL_HOME/tls/cert.pem" -u search:SolrRocks \
  -w '\nHTTP %{http_code}\n' \
  'https://localhost:8984/api/collections/techproducts/select?q=*:*&rows=0&shards.info=true&shards.tolerant=false'
----

Both external HTTPS checks still succeed with the original certificate.
The distributed query through node 2 must fail when its outbound client cannot verify node 1's certificate.
Inspect `tutorial/secure/node2/logs/solr-8984-console.log` or `tutorial/secure/node2/logs/solr.log` for the certificate trust error, such as `SSLHandshakeException` or `PKIX path building failed`.

Restore node 2's normal outbound trust by starting it without the temporary override, then repeat the same query:

[source,bash]
----
bin/solr stop -p 8984
SOLR_LOGS_DIR="$TUTORIAL_HOME/node2/logs" \
  bin/solr start -p 8984 --solr-home "$TUTORIAL_HOME/node2/solr" -z localhost:9983
----

Repeat the collection-state and local-query checks above until node 2's replica is `active`, then run:

[source,bash]
----
curl --fail --cacert "$TUTORIAL_HOME/tls/cert.pem" -u search:SolrRocks \
  'https://localhost:8984/api/collections/techproducts/select?q=*:*&rows=0&shards.info=true&shards.tolerant=false'
----

The distributed query should succeed again with the original total count and HTTPS shard addresses.

== Stop, Restart, and Retain the Configuration

Stop node 2 before node 1, because node 1 hosts ZooKeeper:

[source,bash]
----
bin/solr stop -p 8984
bin/solr stop -p 8983
----

The homes retain indexed data.
Node 1 also retains embedded ZooKeeper data, including the security configuration and ACLs, under `tutorial/secure/node1/solr/zoo_data`.
The private files under `tutorial/secure/tls` retain the key, certificate, passwords, and launch settings.
To restart in a new shell, return to this Solr installation directory and run:

[source,bash]
----
export TUTORIAL_HOME="$PWD/tutorial/secure"
export SOLR_INCLUDE="$TUTORIAL_HOME/tls/solr.in.sh"
SOLR_LOGS_DIR="$TUTORIAL_HOME/node1/logs" \
  bin/solr start -p 8983 --solr-home "$TUTORIAL_HOME/node1/solr"
SOLR_LOGS_DIR="$TUTORIAL_HOME/node2/logs" \
  bin/solr start -p 8984 --solr-home "$TUTORIAL_HOME/node2/solr" -z localhost:9983
----

The certificate expires after 365 days.
Before expiry, replace the certificate and private key, update the trusted certificate in the truststore and PEM file, and restart both nodes with matching trust settings.
Do not replace the truststore with an empty store or disable verification.

To repeat from scratch, stop both nodes and unpack a fresh Solr distribution into a new directory.
This preserves the current exercise and avoids deleting unrelated data.

== Shortcut: Start the Secure Example

After completing the manual exercise, you can create the same kind of demonstration cluster in a fresh installation.
Clear the manual tutorial's include file setting so the shortcut starts with its own configuration:

[source,bash]
----
unset SOLR_INCLUDE
bin/solr start -e secure
----

The shortcut uses `example/secure`, independently of the tutorial's `tutorial/secure` directory.
Stop the manual tutorial nodes first if you use the same ports.
Each invocation stops the nodes recorded in this example's PID directory and replaces its generated certificates, accounts, and collection data.
All contents of the example home are deleted; only pass a dedicated, disposable directory to `--solr-home`.
Stop any other cluster first if it uses the same ports.
The example creates isolated homes in `example/secure/node1/solr` and `example/secure/node2/solr`, plus certificates and configuration in `example/secure/tls`.
Each node writes its logs beside its home, in `node1/logs` or `node2/logs`.
Its include file is `example/secure/tls/solr.in.sh`.
Unlike the manual steps above, the shortcut generates a fresh password each run instead of reusing a fixed one; it prints that password, and the demonstration accounts `admin`, `index`, `search`, `zk-admin`, and `zk-readonly` all use it.
The example performs the setup from this tutorial and prints its configuration path and commands for checking status and stopping the nodes.
Inspect its generated files to connect the automated setup to the manual steps above.

For unattended startup, a different first port, or a separate cluster directory, use the existing start options:

[source,bash]
----
bin/solr start -e secure --no-prompt -p 8993 \
  --solr-home "$PWD/example/secure/another-cluster"
----
