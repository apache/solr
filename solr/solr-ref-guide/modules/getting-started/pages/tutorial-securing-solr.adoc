This exercise starts two SolrCloud nodes, enables HTTPS, assigns separate administration, indexing, and search accounts, and protects ZooKeeper data with access control lists (ACLs).
You will verify HTTPS for both client requests and requests between Solr nodes.
Each step uses the tools included in the Solr distribution, JDK `keytool`, OpenSSL, and `curl`.

Use a fresh full Solr installation on your own machine, with ports 8983, 8984, and 9983 available.
Run the commands in the same Bash-compatible shell, from the installation directory, using an installation path without spaces.
Do not run these commands against an existing cluster.

IMPORTANT: This is a local learning exercise with demonstration passwords and a shared self-signed certificate.
Keep the cluster on loopback.
ZooKeeper authentication and ACLs do not encrypt its connection; this exercise leaves ZooKeeper transport on loopback without TLS.
For deployment guidance, see xref:deployment-guide:securing-solr.adoc[], xref:deployment-guide:enabling-ssl.adoc[], and xref:deployment-guide:zookeeper-access-control.adoc[].

== Start Two Nodes

Start the first node with the ordinary start command:

[source,bash]
----
bin/solr start
----

The default SolrCloud node listens on `localhost:8983`, uses `server/solr` as its Solr home, and starts embedded ZooKeeper on `localhost:9983`.
The embedded ZooKeeper is suitable for this exercise; production clusters should use an external ensemble.

Check that it responds over HTTP, then stop it to choose a ZooKeeper namespace before preparing the second node:

[source,bash]
----
curl --fail 'http://localhost:8983/solr/admin/info/system?wt=json'
bin/solr stop -p 8983
umask 077
export SECURE_WORK="$PWD/example/manual-secure"
mkdir -p "$SECURE_WORK/node2" "$SECURE_WORK/tls"
awk '/<solrcloud>/ { print; print "    <str name=\"zkHost\">localhost:9983/solr</str>"; next } { print }' \
  server/solr/solr.xml > "$SECURE_WORK/solr.xml"
mv "$SECURE_WORK/solr.xml" server/solr/solr.xml
cp server/solr/solr.xml "$SECURE_WORK/node2/"
cp server/solr/zoo.cfg "$SECURE_WORK/node2/"
cat > "$SECURE_WORK/tls/solr.in.sh" <<'EOF'
SOLR_HOST_BIND=127.0.0.1
SOLR_HOST_ADVERTISE=127.0.0.1
ZK_CREATE_CHROOT=true
EOF
export SOLR_INCLUDE="$SECURE_WORK/tls/solr.in.sh"
bin/solr start -p 8983 --solr-home "$PWD/server/solr"
bin/solr start -p 8984 --solr-home "$SECURE_WORK/node2" -z localhost:9983/solr
curl --fail --silent --show-error \
  'http://localhost:8983/solr/admin/collections?action=CLUSTERSTATUS&wt=json'
----

The `awk` command adds `<str name="zkHost">localhost:9983/solr</str>` inside the `<solrcloud>` element of `solr.xml`.
The `/solr` suffix gives this cluster a ZooKeeper namespace, also called a chroot; its paths and security ACLs live beneath that namespace.
The first node still starts embedded ZooKeeper because its start command does not pass `-z`.
`ZK_CREATE_CHROOT=true` lets the launcher create the namespace before Solr connects.
The initial default startup's empty root namespace is no longer used.
The second home copies only configuration files, not the first node's data.

The response's `live_nodes` array must contain two nodes, with ports 8983 and 8984.
If only one node appears, repeat the `curl` command after the second node finishes initializing; continue when both are present.
Both nodes share the first node's ZooKeeper, rather than forming separate clusters.
The working directory will hold the second node's data, certificates, and a private configuration file; the first node continues to use `server/solr`.

== Create a Certificate and PKCS12 Stores

Generate a private key and self-signed certificate directly in a PKCS12 keystore.
The subject alternative names cover both names used in this exercise:

[source,bash]
----
keytool -genkeypair -alias solr -keyalg RSA -keysize 2048 \
  -validity 365 -dname 'CN=localhost' \
  -ext 'SAN=DNS:localhost,IP:127.0.0.1' \
  -storetype PKCS12 -keystore "$SECURE_WORK/tls/solr-keystore.p12" \
  -storepass SolrRocks -keypass SolrRocks
keytool -exportcert -alias solr -rfc \
  -keystore "$SECURE_WORK/tls/solr-keystore.p12" -storetype PKCS12 \
  -storepass SolrRocks -file "$SECURE_WORK/tls/solr-cert.pem"
keytool -importcert -noprompt -alias solr \
  -file "$SECURE_WORK/tls/solr-cert.pem" \
  -keystore "$SECURE_WORK/tls/solr-truststore.p12" -storetype PKCS12 \
  -storepass SolrRocks
openssl x509 -in "$SECURE_WORK/tls/solr-cert.pem" -noout -subject -dates -text
----

The keystore contains the private key and certificate presented by each server.
The truststore contains the certificate trusted by Solr's outbound HTTPS clients.
The PEM certificate lets `curl` verify the server without disabling certificate checks.
Using the same keystore on both nodes simplifies the exercise; real deployments should manage certificates and private keys separately for each node.

== Enable HTTPS on Both Nodes

Write an include file used only for this exercise.
The unquoted heredoc expands the absolute working-directory path now; escaped dollar signs preserve variables for later launches:

[source,bash]
----
cat > "$SECURE_WORK/tls/solr.in.sh" <<EOF
SOLR_HOST_BIND=127.0.0.1
SOLR_HOST_ADVERTISE=127.0.0.1
ZK_CREATE_CHROOT=true
SOLR_SSL_ENABLED=true
SOLR_SSL_KEY_STORE="$SECURE_WORK/tls/solr-keystore.p12"
SOLR_SSL_KEY_STORE_PASSWORD=SolrRocks
SOLR_SSL_KEY_STORE_TYPE=PKCS12
SOLR_SSL_TRUST_STORE="$SECURE_WORK/tls/solr-truststore.p12"
SOLR_SSL_TRUST_STORE_PASSWORD=SolrRocks
SOLR_SSL_TRUST_STORE_TYPE=PKCS12
SOLR_SSL_CLIENT_TRUST_STORE="\${SOLR_SSL_CLIENT_TRUST_STORE:-$SECURE_WORK/tls/solr-truststore.p12}"
SOLR_SSL_CLIENT_TRUST_STORE_PASSWORD=SolrRocks
SOLR_SSL_CLIENT_TRUST_STORE_TYPE=PKCS12
SOLR_SSL_NEED_CLIENT_AUTH=false
SOLR_SSL_WANT_CLIENT_AUTH=false
SOLR_SSL_CHECK_PEER_NAME=true
SOLR_SSL_CLIENT_HOSTNAME_VERIFICATION=true
EOF
chmod 600 "$SECURE_WORK/tls/solr.in.sh"
----

The server's truststore and the outbound client's truststore are explicit.
Nodes advertise the IPv4 loopback address `127.0.0.1`; client URLs can also use `localhost`, because the certificate covers both.
Hostname verification remains enabled.
Client certificates are not required; later steps authenticate users with Basic Authentication over HTTPS.

Before restarting, set the cluster's advertised URL scheme while ZooKeeper is still running.
Then stop the second node before stopping the first node and its embedded ZooKeeper:

[source,bash]
----
bin/solr cluster --property urlScheme --value https -z localhost:9983/solr
bin/solr stop -p 8984
bin/solr stop -p 8983
export SOLR_INCLUDE="$SECURE_WORK/tls/solr.in.sh"
bin/solr start -p 8983 --solr-home "$PWD/server/solr"
bin/solr start -p 8984 --solr-home "$SECURE_WORK/node2" -z localhost:9983/solr
----

Verify each node with the trusted PEM certificate:

[source,bash]
----
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" \
  'https://localhost:8983/solr/admin/info/system?wt=json'
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" \
  'https://127.0.0.1:8984/solr/admin/info/system?wt=json'
----

Both requests should succeed.
A request without the certificate should fail certificate verification, because your operating system does not trust this self-signed certificate.
Plaintext HTTP requests to either port should fail:

[source,bash]
----
curl --fail 'https://localhost:8983/solr/admin/info/system?wt=json'
curl --fail 'http://localhost:8983/solr/admin/info/system?wt=json'
curl --fail 'http://localhost:8984/solr/admin/info/system?wt=json'
----

Do not use `curl -k` to bypass verification.

== Authenticate Users and Assign Roles

Enable Basic Authentication with the existing control-script command.
It writes authentication settings into the private include file and creates `basicAuth.conf` beside it:

[source,bash]
----
SOLR_HOME="$SECURE_WORK/tls" bin/solr auth enable --type basicAuth \
  --credentials solr:SolrRocks --block-unknown true -z localhost:9983/solr
chmod 600 "$SECURE_WORK/tls/basicAuth.conf" "$SOLR_INCLUDE"
----

The security configuration is shared through ZooKeeper, so both nodes enforce it.
The command's `SOLR_HOME` override selects the directory for `basicAuth.conf`; it does not change either running node's home.
The bootstrap account initially has all template roles.
Use the authentication API to set passwords for the indexing and search accounts and remove the unused template `admin` account:

[source,bash]
----
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" -u solr:SolrRocks \
  -H 'Content-Type: application/json' \
  --data '{"set-user":{"index":"SolrRocks","search":"SolrRocks"},"delete-user":["admin"]}' \
  https://localhost:8983/solr/admin/authentication
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" -u solr:SolrRocks \
  -H 'Content-Type: application/json' \
  --data '{"set-user-role":{"solr":["superadmin","admin"],"index":["index","search"],"search":["search"],"admin":null}}' \
  https://localhost:8983/solr/admin/authorization
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" -u solr:SolrRocks \
  https://localhost:8983/solr/admin/authorization
----

Inspect the permission list in the last response.
In the built-in template, `collection-admin-read` is permission index 9 and grants only the `search` role.
Allow both `admin` and `search` to inspect collection state:

[source,bash]
----
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" -u solr:SolrRocks \
  -H 'Content-Type: application/json' \
  --data '{"update-permission":{"index":9,"role":["admin","search"]}}' \
  https://localhost:8983/solr/admin/authorization
----

The accounts now have these responsibilities:

[cols="1,2",options="header"]
|===
|Account |Permissions
|`solr` |Manage security, configuration, and collections; cannot index or search.
|`index` |Index documents and search.
|`search` |Search; cannot index documents.
|===

The predefined `read` and `update` permissions take precedence over the template's final `all` permission.
Removing `index` and `search` roles from `solr` therefore separates administration from document access.
For permission details, see xref:deployment-guide:rule-based-authorization-plugin.adoc[].

== Protect ZooKeeper Data

Solr user accounts do not protect direct ZooKeeper access.
Create separate digest credentials for ZooKeeper administration and read-only inspection:

[source,bash]
----
cat > "$SECURE_WORK/tls/zk-credentials.properties" <<'EOF'
zkDigestUsername=zk-admin
zkDigestPassword=SolrRocks
zkDigestReadonlyUsername=zk-readonly
zkDigestReadonlyPassword=SolrRocks
EOF
chmod 600 "$SECURE_WORK/tls/zk-credentials.properties"
printf '\n' >> "$SOLR_INCLUDE"
cat >> "$SOLR_INCLUDE" <<EOF
SOLR_ZK_CREDS_AND_ACLS="-DzkCredentialsInjector=org.apache.solr.common.cloud.VMParamsZkCredentialsInjector -DzkCredentialsProvider=org.apache.solr.common.cloud.DigestZkCredentialsProvider -DzkACLProvider=org.apache.solr.common.cloud.DigestZkACLProvider -DzkDigestCredentialsFile=$SECURE_WORK/tls/zk-credentials.properties"
SOLR_OPTS="\$SOLR_OPTS \$SOLR_ZK_CREDS_AND_ACLS"
EOF
bin/solr stop -p 8984
bin/solr stop -p 8983
bin/solr start -p 8983 --solr-home "$PWD/server/solr"
bin/solr start -p 8984 --solr-home "$SECURE_WORK/node2" -z localhost:9983/solr
bin/solr zk updateacls / -z localhost:9983/solr
----

`SOLR_ZK_CREDS_AND_ACLS` configures command-line ZooKeeper clients; adding the same settings to `SOLR_OPTS` also configures each server.
The servers authenticate as `zk-admin` and create znodes with administrator access plus read-only access for `zk-readonly`.
Within the `/solr` namespace, the ACL provider grants only the administrator access to sensitive paths such as `/security.json`.
The final `updateacls` command migrates existing znodes: changing the provider alone would leave their previous ACLs in place.

Check administrator access:

[source,bash]
----
bin/solr zk ls / -z localhost:9983/solr
----

For a read-only CLI session, pass only the read-only user's credentials, using the injector's primary username/password fields.
This authenticates the client as that user without supplying the administrator secret:

[source,bash]
----
READONLY_ZK_OPTS='-DzkCredentialsInjector=org.apache.solr.common.cloud.VMParamsZkCredentialsInjector -DzkCredentialsProvider=org.apache.solr.common.cloud.DigestZkCredentialsProvider -DzkDigestUsername=zk-readonly -DzkDigestPassword=SolrRocks'
SOLR_INCLUDE=/dev/null SOLR_ZK_CREDS_AND_ACLS="$READONLY_ZK_OPTS" \
  bin/solr zk ls /collections -z localhost:9983/solr
printf 'read-only probe\n' > "$SECURE_WORK/readonly-probe.txt"
SOLR_INCLUDE=/dev/null SOLR_ZK_CREDS_AND_ACLS="$READONLY_ZK_OPTS" \
  bin/solr zk cp "$SECURE_WORK/readonly-probe.txt" zk:/readonly-probe -z localhost:9983/solr
SOLR_INCLUDE=/dev/null SOLR_ZK_CREDS_AND_ACLS="$READONLY_ZK_OPTS" \
  bin/solr zk cp zk:/security.json "$SECURE_WORK/forbidden-security.json" -z localhost:9983/solr
SOLR_INCLUDE=/dev/null SOLR_ZK_CREDS_AND_ACLS= \
  bin/solr zk ls / -z localhost:9983/solr
----

The directory listing as `zk-readonly` succeeds.
The attempted write, the read of `security.json`, and the anonymous listing must fail with authorization errors.
These ACLs control access but do not provide transport encryption.

== Index and Verify Distributed HTTPS Queries

Create a collection with two shards and one replica per shard, using the techproducts configuration, then index the sample XML documents as `index`:

[source,bash]
----
bin/solr create -c techproducts --shards 2 --replication-factor 1 \
  -d sample_techproducts_configs --credentials solr:SolrRocks \
  -s https://localhost:8983
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" -u solr:SolrRocks \
  'https://localhost:8983/solr/admin/collections?action=CLUSTERSTATUS&collection=techproducts&wt=json'
bin/solr post -c techproducts --credentials index:SolrRocks \
  -s https://localhost:8983 example/exampledocs/*.xml
----

Check that collection state reports one shard replica on port 8983 and the other on port 8984, both `active`, with `https://` base URLs.
Each node should hold only part of the collection.

Query through both nodes as `search`, asking Solr to include shard details:

[source,bash]
----
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" -u search:SolrRocks \
  'https://localhost:8983/solr/techproducts/select?q=*:*&rows=0&shards.info=true'
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" -u search:SolrRocks \
  'https://localhost:8984/solr/techproducts/select?q=*:*&rows=0&shards.info=true'
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" -u search:SolrRocks \
  'https://localhost:8983/solr/techproducts/select?q=*:*&rows=0&distrib=false'
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" -u search:SolrRocks \
  'https://localhost:8984/solr/techproducts/select?q=*:*&rows=0&distrib=false'
----

The distributed requests return the same total `numFound` and show two responding shard addresses under `shards.info`.
The bundled XML examples produce 31 documents.
Every address must start with `https://`, including the remote node.
With `distrib=false`, each node returns its local shard's count; the two local counts add up to the distributed total.
This confirms that a full query requires communication between the nodes.

Verify the role boundaries and anonymous access.
The first three requests should return HTTP 403; the last two should return HTTP 401:

[source,bash]
----
curl --cacert "$SECURE_WORK/tls/solr-cert.pem" -u search:SolrRocks \
  -H 'Content-Type: application/json' --data '[{"id":"forbidden"}]' \
  -w '\nHTTP %{http_code}\n' https://localhost:8983/solr/techproducts/update
curl --cacert "$SECURE_WORK/tls/solr-cert.pem" -u solr:SolrRocks \
  -w '\nHTTP %{http_code}\n' 'https://localhost:8983/solr/techproducts/select?q=*:*'
curl --cacert "$SECURE_WORK/tls/solr-cert.pem" -u solr:SolrRocks \
  -H 'Content-Type: application/json' --data '[{"id":"forbidden-admin"}]' \
  -w '\nHTTP %{http_code}\n' https://localhost:8983/solr/techproducts/update
curl --cacert "$SECURE_WORK/tls/solr-cert.pem" -w '\nHTTP %{http_code}\n' \
  'https://localhost:8983/solr/techproducts/select?q=*:*'
curl --cacert "$SECURE_WORK/tls/solr-cert.pem" -w '\nHTTP %{http_code}\n' \
  'https://localhost:8984/solr/techproducts/select?q=*:*'
----

== Test Trust Between the Nodes

A successful `curl` request verifies curl's trust in the server.
To also test the outbound trust used by Solr, temporarily give node 2 a truststore containing an unrelated certificate.
Keep the normal server keystore and truststore unchanged:

[source,bash]
----
keytool -genkeypair -alias unrelated -keyalg RSA -keysize 2048 \
  -validity 1 -dname 'CN=unrelated' -storetype PKCS12 \
  -keystore "$SECURE_WORK/tls/unrelated-keystore.p12" \
  -storepass SolrRocks -keypass SolrRocks
keytool -exportcert -alias unrelated -rfc -storetype PKCS12 \
  -keystore "$SECURE_WORK/tls/unrelated-keystore.p12" -storepass SolrRocks \
  -file "$SECURE_WORK/tls/unrelated-cert.pem"
keytool -importcert -noprompt -alias unrelated -storetype PKCS12 \
  -file "$SECURE_WORK/tls/unrelated-cert.pem" \
  -keystore "$SECURE_WORK/tls/untrusted-truststore.p12" -storepass SolrRocks
bin/solr stop -p 8984
SOLR_SSL_CLIENT_TRUST_STORE="$SECURE_WORK/tls/untrusted-truststore.p12" \
  bin/solr start -p 8984 --solr-home "$SECURE_WORK/node2" -z localhost:9983/solr
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" -u solr:SolrRocks \
  'https://localhost:8983/solr/admin/info/system?wt=json'
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" -u solr:SolrRocks \
  'https://localhost:8984/solr/admin/info/system?wt=json'
----

Wait for node 2's replica to finish loading before testing the distributed query.
Inspect collection state and confirm a local query succeeds:

[source,bash]
----
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" -u solr:SolrRocks \
  'https://localhost:8983/solr/admin/collections?action=CLUSTERSTATUS&collection=techproducts&wt=json'
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" -u search:SolrRocks \
  'https://localhost:8984/solr/techproducts/select?q=*:*&rows=0&distrib=false'
----

Repeat these checks until both replicas are `active` and the local query returns node 2's document count.
Then issue the distributed query:

[source,bash]
----
curl --cacert "$SECURE_WORK/tls/solr-cert.pem" -u search:SolrRocks \
  -w '\nHTTP %{http_code}\n' \
  'https://localhost:8984/solr/techproducts/select?q=*:*&rows=0&shards.info=true&shards.tolerant=false'
----

Both external HTTPS checks still succeed with the original certificate.
The distributed query through node 2 must fail when its outbound client cannot verify node 1's certificate.
Inspect `example/manual-secure/logs/solr-8984-console.log` or `example/manual-secure/logs/solr.log` for the certificate trust error, such as `SSLHandshakeException` or `PKIX path building failed`.

Restore node 2's normal outbound trust by starting it without the temporary override, then repeat the same query:

[source,bash]
----
bin/solr stop -p 8984
bin/solr start -p 8984 --solr-home "$SECURE_WORK/node2" -z localhost:9983/solr
----

Repeat the collection-state and local-query checks above until node 2's replica is `active`, then run:

[source,bash]
----
curl --fail --cacert "$SECURE_WORK/tls/solr-cert.pem" -u search:SolrRocks \
  'https://localhost:8984/solr/techproducts/select?q=*:*&rows=0&shards.info=true&shards.tolerant=false'
----

The distributed query should succeed again with the original total count and HTTPS shard addresses.

== Stop, Restart, and Retain the Configuration

Stop node 2 before node 1, because node 1 hosts ZooKeeper:

[source,bash]
----
bin/solr stop -p 8984
bin/solr stop -p 8983
----

The homes retain indexed data; `server/solr` also retains embedded ZooKeeper data, including the security configuration and ACLs.
The private files under `example/manual-secure/tls` retain the key, certificate, passwords, and launch settings.
To restart in a new shell, return to this Solr installation directory and run:

[source,bash]
----
export SECURE_WORK="$PWD/example/manual-secure"
export SOLR_INCLUDE="$SECURE_WORK/tls/solr.in.sh"
bin/solr start -p 8983 --solr-home "$PWD/server/solr"
bin/solr start -p 8984 --solr-home "$SECURE_WORK/node2" -z localhost:9983/solr
----

The certificate expires after 365 days.
Before expiry, replace the certificate and private key, update the trusted certificate in the truststore and PEM file, and restart both nodes with matching trust settings.
Do not replace the truststore with an empty store or disable verification.

To repeat from scratch, stop both nodes and unpack a fresh Solr distribution into a new directory.
This preserves the current exercise and avoids deleting unrelated data from `server/solr`.

== Shortcut: Start the Secure Example

After completing the manual exercise, you can create the same kind of demonstration cluster in a fresh installation with:

[source,bash]
----
bin/solr start -e secure
----

Stop the manual cluster first if using the same ports.
The example creates isolated homes in `example/secure/cluster/node1/solr` and `example/secure/cluster/node2/solr`, plus certificates and configuration in `example/secure/cluster/tls`.
Each node writes its logs beside its home, in `node1/logs` or `node2/logs`.
Its include file is `example/secure/cluster/tls/solr.in.sh`.
The demonstration accounts `solr`, `index`, `search`, `zk-admin`, and `zk-readonly` all use the password `SolrRocks`.
The example prints commands for verifying the resulting cluster; inspect its files to connect the automated setup to the manual steps above.

For unattended startup, a different first port, or a separate cluster directory, use the existing start options:

[source,bash]
----
bin/solr start -e secure --no-prompt -p 8993 \
  --solr-home "$PWD/example/secure/another-cluster"
----

The second node uses the next port; embedded ZooKeeper uses the first port plus 1000.
Re-running the example with the same directory reuses its certificate, accounts, and collection data.
The example supports `--no-prompt`, `-p`, `--solr-home`, and `--force`; other startup overrides are not supported.
