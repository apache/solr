This tutorial introduces authentication and authorization using a single-node SolrCloud example.
You will configure HTTPS and ZooKeeper access control, verify the certificate with curl, create users with Basic Authentication and Rule-Based Authorization, and try requests with different permissions.
The example loads the same techproducts data used in xref:tutorial-techproducts.adoc[].

Authentication identifies the user making a request.
Authorization determines what that user may do.
A correct password does not grant access to every API: the user's roles must also allow the requested operation.

== Before You Begin

Run the commands from your Solr installation directory.
This tutorial assumes you are familiar with the basics in xref:solr-tutorial.adoc[].
The examples use `curl` and OpenSSL from a Unix or macOS terminal.

[WARNING]
====
This is a local learning environment with demonstration passwords.
The wizard configures HTTPS before asking for users and passwords.
Basic Authentication does not encrypt credentials; use TLS for connections outside this local example.
A production deployment also needs network restrictions and a secured ZooKeeper ensemble.
See xref:deployment-guide:securing-solr.adoc[] for deployment guidance.
====

== Start the Secure Example

[source,bash]
----
bin/solr start -e secure-setup
----

The example starts one SolrCloud node on port 8983 with embedded ZooKeeper.
The startup command sets `-Dsolr.environment=prod,label=Secure+Solr+Setup` to label the Admin UI as "Secure Solr Setup".
It creates a `techproducts` collection with one shard and one replica, using `sample_techproducts_configs`, and indexes 31 sample documents.

The default Solr home is `example/secure-setup`.
Use `--solr-home` to choose a different, existing directory or `-p` to choose a different Solr port (at most 64535); substitute your directory and port in the commands below.
The embedded ZooKeeper port is the Solr port plus 1000.
See xref:deployment-guide:solr-control-script-reference.adoc#start-and-restart[Start and Restart] for the available startup options.

=== Configure HTTPS

On Unix and macOS, the wizard first offers to generate a self-signed localhost certificate or use existing PEM files:

[source,text]
----
Generate a localhost certificate or use existing PEM files? [G/p]:
Keystore password [SolrRocks]:
----

Press Enter to generate a certificate covering `localhost` and `127.0.0.1`, valid for 30 days.
The keystore password must contain at least six characters.
Choose `P` instead to supply your PEM certificate chain, private key, keystore password file, and optionally a password file for an encrypted private key.
Existing certificates must cover the hostname used by clients and other Solr nodes.

The example uses `bin/solr ssl`'s conversion logic and stores its certificate, keystore, truststore, and include file under `example/secure-setup/tls`.
It does not edit the installation-wide `solr.in.sh`.
On a fresh example, Solr starts with HTTPS before user setup.

=== Configure ZooKeeper Access Control

Before starting Solr, the wizard also asks for passwords for separate ZooKeeper digest accounts:

[source,text]
----
Password for zk-admin [SolrRocks]:
Password for zk-readonly [SolrRocks]:
----

`zk-admin` has full access to the example's ZooKeeper data.
`zk-readonly` can read ordinary metadata but cannot modify it or read `/security.json` and `/security/*`.
These accounts are independent of the HTTP users configured below.
Credentials are saved in `example/secure-setup/zk-credentials.properties`, with owner-only permissions on POSIX filesystems.
The example-specific include file configures digest authentication and ACLs for both Solr and CLI commands, using the `/solr` ZooKeeper chroot.

=== Verify HTTPS

The wizard starts Solr, prints a command like this, and pauses:

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem \
  'https://localhost:8983/api/node/system'
----

Run the command in another terminal.
You should receive system information without a certificate error.
Return to the wizard and press Enter to continue with user setup.
The wizard does not run curl itself.
If you are restarting an example with authentication enabled, an HTTP 401 response also confirms that HTTPS is working; administrator credentials are requested before starting that existing example.

On Windows, the wizard configures HTTP users only; configure them manually as described in xref:deployment-guide:zookeeper-access-control.adoc[] and xref:deployment-guide:enabling-ssl.adoc[].
The remaining commands in this tutorial assume the Unix or macOS HTTPS setup.

=== Choose Users and Passwords

The interactive session asks for an administrator, then passwords for the fixed `index` and `search` accounts:

[source,text]
----
Administrator username [solr]:
Administrator password [SolrRocks]:
Password for index [SolrRocks]:
Password for search [SolrRocks]:
----

Press Enter at each prompt to accept the defaults used throughout this tutorial.
You can choose a different administrator username and set your own passwords; substitute those credentials in later commands.
The usernames `index` and `search` are reserved for the data-access accounts, and the administrator username cannot contain a colon.
A password equal to its username is rejected by default; the wizard asks for another password.
Passwords typed at an interactive terminal are hidden.

[%autowidth,options="header"]
|===
|Username |Default password |Access
|`solr` |`SolrRocks` |Security, collection, and configuration administration; no document indexing or searching
|`index` |`SolrRocks` |Indexing and searching
|`search` |`SolrRocks` |Searching
|===

For a non-interactive start with a generated certificate and the default HTTP and ZooKeeper accounts (all passwords `SolrRocks`):

[source,bash]
----
bin/solr start -e secure-setup --no-prompt
----

`--no-prompt` prints the curl verification command but does not pause for you to run it.

Saved ZooKeeper credentials are reused on subsequent starts.
An existing example with unsecured ZooKeeper data requires a fresh Solr home or an offline ACL migration; the wizard does not rewrite existing ACLs while Solr is running.
See xref:deployment-guide:zookeeper-access-control.adoc[] for migration instructions and production considerations, including ZooKeeper transport security.

=== Where Security Is Stored

The example uses `example/secure-setup` as its Solr home.
It starts the node, writes the security configuration to `/security.json` within the ZooKeeper `/solr` chroot, and waits for authentication to become active before creating the collection or indexing data.

The configuration uses these plugins:

[source,json]
----
{
  "authentication": {
    "class": "solr.BasicAuthPlugin",
    "blockUnknown": true
  },
  "authorization": {
    "class": "solr.RuleBasedAuthorizationPlugin"
  }
}
----

This excerpt only shows the plugin settings.
The complete configuration also contains salted password hashes, user-to-role mappings, and permission rules.
The administrator has only the `superadmin` and `admin` roles.
Collection metadata remains available to the administrator, but document reads and updates require the data-access roles.
The indexing user has `index` and `search`; the search-only user has `search`.
The wizard loads the sample documents over HTTPS using the `index` account.

In SolrCloud, security settings are shared through ZooKeeper.
Editing a local `security.json` file in the Solr home does not change the cluster configuration.

== Sign In to the Admin UI

Open https://localhost:8983/solr/[the Solr Admin UI] in your browser.
Accept the browser warning for the self-signed certificate generated for this local example.
Sign in with username `solr` and password `SolrRocks`, unless you chose different administrator credentials.

The Security screen lets the administrator inspect and manage users, roles, and permissions.
To query documents in the Admin UI, sign in as `search` or `index`, select the `techproducts` collection, and open its Query screen.
Run the default `\*:*` query to see the sample documents.
An administrator query or document update receives HTTP 403 because those data-access roles are not assigned to the administrator.

== Try Authentication and Authorization

=== Query Without Credentials

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem -i 'https://localhost:8983/solr/techproducts/select?q=*:*&rows=0'
----

The request returns HTTP `401 Unauthorized` because it has no credentials.
The `blockUnknown` setting requires authentication.
An incorrect password also produces a 401 response.

=== Query as the Search User

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem --user search:SolrRocks 'https://localhost:8983/solr/techproducts/select?q=*:*&rows=0'
----

This request succeeds.
The response's `numFound` value is `31` on a fresh example.
The search user's role grants the `read` permission.

=== Try an Update as the Search User

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem -i --user search:SolrRocks \
  -H 'Content-Type: application/json' \
  --data-binary '[{"id":"secure-example-product","name":"Secure example product"}]' \
  'https://localhost:8983/solr/techproducts/update?commit=true'
----

This request returns HTTP `403 Forbidden`.
The password is valid, but the user's roles do not grant the `update` permission.
The document is not added.

=== Index as the Indexing User

Send the same update using the indexing account:

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem --user index:SolrRocks \
  -H 'Content-Type: application/json' \
  --data-binary '[{"id":"secure-example-product","name":"Secure example product"}]' \
  'https://localhost:8983/solr/techproducts/update?commit=true'
----

This request succeeds because the indexing user's `index` role grants `update`.
Query the new document with the search account:

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem --user search:SolrRocks \
  'https://localhost:8983/solr/techproducts/select?q=id:secure-example-product'
----

== Create Another Search User

Creating an account and assigning its permissions are separate steps.
As the administrator, create a user named `reader`:

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem --user solr:SolrRocks \
  -H 'Content-Type: application/json' \
  --data-binary '{"set-user":{"reader":"ReaderRocks"}}' \
  'https://localhost:8983/solr/admin/authentication'
----

Assign the existing `search` role to that user:

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem --user solr:SolrRocks \
  -H 'Content-Type: application/json' \
  --data-binary '{"set-user-role":{"reader":["search"]}}' \
  'https://localhost:8983/solr/admin/authorization'
----

The node reloads security changes asynchronously.
Once the new configuration has loaded, query with the new credentials:

[source,bash]
----
curl --cacert example/secure-setup/tls/cert.pem --user reader:ReaderRocks 'https://localhost:8983/solr/techproducts/select?q=*:*&rows=0'
----

For details on changing passwords and permission rules, see xref:deployment-guide:basic-authentication-plugin.adoc[] and xref:deployment-guide:rule-based-authorization-plugin.adoc[].

== Stop and Restart

[source,bash]
----
bin/solr stop -p 8983
----

Run `bin/solr start -e secure-setup` again to restart the example.
Existing security settings are preserved, and an existing collection is not reindexed.
Enter the credentials of an existing administrator; the prompts do not reset passwords or replace the saved configuration.
The `index` and `search` password prompts also leave their existing passwords unchanged.
If you changed the administrator password, `--no-prompt` will still try the original demonstration credentials and will not authenticate.

== Use the CLI with the Secured Example

=== Reuse the Example Settings

Subsequent runs reuse the certificate and HTTPS settings under `example/secure-setup/tls`.
The generated self-signed certificate is intended only for this local exercise.
Your browser will warn about it; a certificate from a publicly trusted CA avoids that warning.

Other `bin/solr` commands can use the example's HTTPS and ZooKeeper credentials by selecting its include file.
For example, check the node's status with the HTTP administrator credentials:

[source,bash]
----
SOLR_INCLUDE=example/secure-setup/tls/solr.in.sh bin/solr status --credentials solr:SolrRocks
----

To inspect ZooKeeper metadata with the configured `zk-admin` credentials, select the same include file and specify the ZooKeeper connection string:

[source,bash]
----
SOLR_INCLUDE=example/secure-setup/tls/solr.in.sh bin/solr zk ls / --zk-host localhost:9983/solr
----

The output lists the example's znodes, including `collections`, `configs`, and `security.json`.
The HTTP `--credentials` option does not authenticate ZooKeeper requests; the include file selects the saved ZooKeeper credentials.

Compare this with a request that does not load the example's credentials:

[source,bash]
----
SOLR_INCLUDE=/dev/null SOLR_ZK_CREDS_AND_ACLS='' bin/solr zk ls / --zk-host localhost:9983/solr
----

This command fails with `NoAuth`, demonstrating that the ACLs require authentication for access to the example's data.


=== Replace or Renew the Certificate

To replace or renew the certificate, use `bin/solr ssl` with `--solr-include-file example/secure-setup/tls/solr.in.sh` and `--keystore example/secure-setup/tls/solr-ssl.keystore.jks`.
Also update `example/secure-setup/tls/cert.pem` and `example/secure-setup/tls/keystore-password.txt` to match the new certificate and keystore password before restarting the example.
See xref:deployment-guide:enabling-ssl.adoc#install-an-existing-pem-certificate[Install an Existing PEM Certificate] for details.
