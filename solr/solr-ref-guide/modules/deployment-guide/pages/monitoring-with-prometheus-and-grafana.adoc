[IMPORTANT]
====
*Work in progress — the artifacts shipped today are placeholders.*

Solr 10 removed the standalone `solr-exporter` (the `prometheus-exporter` module) and now exposes metrics natively, under OpenTelemetry-based metric names.
Dashboards and alert rules written against the old exporter therefore do not work on Solr 10 or later: the process they scraped is gone, and the metric names and labels they query have changed.
Solr's own dashboard and alert rules are consequently being built from scratch, panel by panel and rule by rule.

What is in `solr/monitoring/` right now is a two-panel dashboard and a single alert, present to prove the generation pipeline works — not a monitoring setup to deploy.
The dashboard worth deploying arrives in https://issues.apache.org/jira/browse/SOLR-18534[SOLR-18534] and the alert rules in https://issues.apache.org/jira/browse/SOLR-18535[SOLR-18535].
Expect both files, and this page, to change substantially before they are useful.
====

Solr ships three monitoring artifacts in `solr/monitoring/`:

* `grafana-solr-dashboard.json` — a Grafana dashboard
* `prometheus-solr-alerts.yml` — a set of Prometheus alert rules
* `otel-collector-config.yaml` — an example OpenTelemetry Collector configuration, for the <<otlp-push,OTLP push>> option

Import the first two into your own Prometheus + Grafana installation.
Solr exposes all metrics natively, so no exporter process is required.
For the full list of available metrics see xref:metrics-reporting.adoc[].

[[metrics-collection]]
== Getting Metrics into Prometheus

There are two ways to get Solr metrics into Prometheus.

[[prometheus-scrape]]
=== Option 1: Prometheus Pull (recommended)

Prometheus scrapes each Solr node directly — no extra process needed.
Add a scrape job to your `prometheus.yml`:

[source,yaml]
----
scrape_configs:
  - job_name: solr                        # <1>
    metrics_path: /solr/admin/metrics     # <2>
    scrape_interval: 15s
    static_configs:
      - targets: ['solr-node1:8983', 'solr-node2:8983']
----
<1> The dashboard and alert rules select on this job name.
    If you use another, set `solrSelector` to match — see <<customizing>>.
<2> Solr 10.1 and later also serve this at the shorter v2 alias `/api/metrics`.

Scrape every node rather than one: each reports its own JVM and the cores it hosts.
If metrics collection is switched off for a node, both endpoints answer `HTTP 510` and Prometheus marks the target down.

[[otlp-push]]
=== Option 2: OTLP Push via OpenTelemetry Collector

With the xref:opentelemetry.adoc[`opentelemetry` module] enabled and `solr.metrics.otlpExporterEnabled=true` on every node (see xref:metrics-reporting.adoc#otlp[OTLP]), each node pushes its metrics to an https://opentelemetry.io/docs/collector/[OpenTelemetry Collector], and Prometheus scrapes the Collector instead of the nodes.
The Collector can forward the same stream to any other OTLP-compatible backend as well.

Start from the example `solr/monitoring/otel-collector-config.yaml` (it needs the `otel/opentelemetry-collector-contrib` distribution, and is a starting point to adapt rather than a production configuration).
It receives OTLP on `:4317` (gRPC) and `:4318` (HTTP), serves the result in Prometheus format on `:9464`, and forwards the raw stream to an https://aspire.dev/dashboard/[Aspire Dashboard], which you can remove.
Its `transform` processor is what makes the names identical to Option 1: the Collector would otherwise append `_ratio` to dimensionless metrics such as `jvm_cpu_recent_utilization`, which Solr's own endpoint does not, and it supplies `service.name=solr` for Solr versions that send the SDK default, so the `job` label stays `solr`.

Then scrape the Collector:

[source,yaml]
----
scrape_configs:
  - job_name: solr
    honor_labels: true                      # <1>
    scrape_interval: 15s
    static_configs:
      - targets: ['otel-collector:9464']
----
<1> Keep the `job` and `instance` labels the Collector derives from Solr's `service.name` and `service.instance.id` resource attributes, rather than Prometheus overwriting them with the Collector's own address.

The series Prometheus stores then carry the same metric names, types and label keys as a direct scrape.
Two differences remain until https://issues.apache.org/jira/browse/SOLR-18594[SOLR-18594] makes Solr send `service.instance.id`: the `instance` label is the Collector's address rather than the node's, so per-node panels show one merged series, and no `target_info` series is produced.

Alternatively the Collector can push into Prometheus instead of being scraped — with its `prometheusremotewrite` exporter against Prometheus started with `--web.enable-remote-write-receiver`, or its `otlphttp` exporter against `--web.enable-otlp-receiver`.
The shipped configuration and the name parity above are only verified for the scrape setup; Prometheus's OTLP receiver applies its own name translation.

[[alert-rules]]
== Alert Rules

Reference `prometheus-solr-alerts.yml` from your `prometheus.yml`:

[source,yaml]
----
rule_files:
  - /path/to/prometheus-solr-alerts.yml
----

Validate the file before deploying it, and after any edit:

[source,bash]
----
promtool check rules prometheus-solr-alerts.yml
----

Rules carry a `severity` label for routing in Alertmanager.
One placeholder rule is included today:

[cols="2,1,3",options="header"]
|===
| Alert | Severity | Fires when
| `SolrNodeDown` | warning | A Solr target has failed to scrape for 2 minutes
|===

NOTE: The rules covering heap, GC, disk, latency, error rate and SolrCloud health arrive in https://issues.apache.org/jira/browse/SOLR-18535[SOLR-18535].

[[customizing]]
== Customizing the Artifacts

Both artifacts are generated from a https://jsonnet.org/[jsonnet] mixin source in `solr/monitoring/mixin/`, following the conventions of the https://github.com/monitoring-mixins/docs[monitoring-mixins] community.
Edit the jsonnet, not the generated output.

Tunable settings are centralized in `mixin/config.libsonnet`:

[source,jsonnet]
----
{
  _config:: {
    solrSelector: 'job="solr"',   // label selector identifying Solr targets
    rateInterval: '5m',           // window for rate() queries
  },
}
----

`solrSelector` is applied to every dashboard query and alert expression, so JVM metrics scraped from other Java services are not read as Solr's.
Either edit the file and regenerate, or leave this tree untouched and patch the configuration from your own jsonnet:

[source,jsonnet]
----
(import 'mixin.libsonnet') + { _config+:: { solrSelector: 'job="my-solr"' } }
----

Regenerating requires `jsonnet`, `jsonnet-bundler` and `gojsontoyaml`, or the included Docker wrapper that supplies all three:

[source,bash]
----
cd solr/monitoring/mixin
./make.sh install   # fetch jsonnet dependencies
./make.sh all       # regenerate both artifacts
----

See `solr/monitoring/README.md` for the remaining build targets and the local toolchain alternative.

[[dev-stack]]
== Trying It Locally

The Solr source tree carries a docker-compose stack that runs Solr, Prometheus, Grafana and Alertmanager together with the generated artifacts already wired in.
It exists to make changes to those artifacts easy to see, and is contributor tooling rather than a deployment to model yours on — it is not part of the Solr release.

[source,bash]
----
cd solr/monitoring/dev
./stack.sh
----

Grafana is then on `http://localhost:3000`, opening directly on the provisioned dashboard, with Prometheus on `:9090` and Alertmanager on `:9093`.
`./stack.sh --local-solr` skips the bundled Solr nodes and scrapes a Solr you are already running.
`./stack.sh --metrics-scrape=otel` makes Prometheus scrape the stack's OpenTelemetry Collector, which the Solr nodes push to, instead of the nodes — the two options above side by side.
The Collector also forwards what the nodes push, metrics and traces, to an Aspire Dashboard on `:18888`, a convenient raw view of the OTLP data.

[[distributed-tracing]]
== Metrics and Tracing Together

The same xref:opentelemetry.adoc[OpenTelemetry] instrumentation that produces these metrics also emits xref:distributed-tracing.adoc[distributed traces], so a latency spike on the dashboard can be followed into the traces of the requests that caused it.
Both signals are exported via OTLP and can flow through the same Collector pipeline to a unified observability backend, or independently to specialized ones.
